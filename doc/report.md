### 1. 課題の概要と目的

市販されているリモート操作可能な二輪走行ロボット「ROBOBIKE」に、講義で学んだ ROS2 と模倣学習を適用し、人の操作を学習した AI による操舵を目指した。スマートフォンで操作する既存機体を対象に、外部から観測・操作・記録できる仕組みを構築することで、既存のロボットに Physical AI を導入する際の設計と実装を理解することを目的とした。

設定したタスクは、俯瞰カメラ画像と機体状態に基づき、走行コースに沿うように操舵することである。実装範囲を段階化し、**操舵は学習済み方策、速度は人のゲームパッド操作**とした。現時点ではデータ収集から学習・推論・実機へのコマンド送信までを接続したが、**学習済み方策による走行の実現には至っていない**。

### 2. 実機とシステム構成

ROBOBIKEは、ESP32-C3を搭載し、Wi-Fi経由で操作できる二輪ロボットである。回路図やファームウェアは公開されているがライセンスが明記されていなかったため、機体の駆動系・制御基板・ファームウェアは改変せず、既存の HTTP API を利用した。なお、実験時には搭載人形を変更している。機体に備わるバランス制御は既存ファームウェアが担当し、本課題ではその上位に操舵方策を追加した。

| 構成要素 | 使用機器・役割 |
|---|---|
| ROBOBIKE | 前輪操舵、後輪駆動、スタンド制御。既存APIから操作・状態取得 |
| Bridge側 | RaspberryPi5(16 GB)。ROS2 と HTTP の橋渡し、データ収集・保存 |
| 観測・手動操作 | USB 書画カメラによる俯瞰画像、XBox 互換ゲームパッド |
| Policy側 | GeForceRTX3080 搭載 Linux PC。LeRobot ACTの学習・推論 |
| ソフトウェア | Ubuntu 26.04 LTS、ROS2 Lyrical Luth、OpenCV、LeRobot 0.6.1 |

通信は、**PC ⇄ ROS2/DDS ⇄ RaspberryPi ⇄ Wi-Fi/HTTP ⇄ ROBOBIKE**という構成とした。RaspberryPi (以後Piと呼称)は機体用 Wi-Fi と PC との通信回線を使い分ける。画像は 320×240 画素の JPEG を 10Hzで配信し、学習用の生データは Pi 上に保存する。推論の計算負荷を GPU 搭載 PC に分担させることで、機体との接続処理と AI 処理を分離した。

### 3. AIの活用と処理の流れ

人がゲームパッドで操縦した記録を教師データとして、LeRobot の ACT(Action Chunking with Transformers) を学習する。ACT は観測から一連の行動を予測する模倣学習の方策であり、今回の AI 活用は操舵値の生成に当たる。既存ファームウェアのバランス制御自体を学習で置き換えるものではない。

| 方策の入出力 | 内容 |
|---|---|
| 画像入力 | 俯瞰カメラ画像、320×240 画素、RGB |
| 状態入力 | 駆動・操舵・スタンド出力、操舵サーボ位置、3軸角速度、3軸加速度、速度設定値の計11項目 |
| 学習時の行動 | 操舵値（−1〜1に正規化）と速度設定値の2項目 |
| 実機に適用する出力 | 操舵値のみ。−100〜100の操作値に変換し、既存の操舵APIへ送信 |
| 制御設定 | 10Hz。推論ノードでは既定で予測行動列の10ステップ分を使用 |

速度設定値はデータ形式への対応と将来の拡張のために行動に含めているが、推論時の速度操作には使用しない。

1. **記録**：画像、テレメトリ、ステータス、操作コマンド、エピソード開始・終了イベントを rosbag2 の MCAP 形式で保存する。START で記録対象の操作区間を開始し、BACK/LB/ゲームパッド切断で終了する。
2. **データ変換**：操作区間を 10Hz に区切り、Pi 上の bag 記録時刻を基準に、各時刻以前の最新の観測と操作を対応付ける。必要な観測が欠けるフレームは採用せず、古い観測には警告を出す。不要なエピソードは指定して除外できる。
3. **学習**：変換した LeRobot Dataset を使い、PC の GPU 上で ACT を学習する。画像・状態・行動の定義を共通モジュール化し、変換時と推論時で入出力の意味を揃える。
4. **推論と送信**：PC が ROS2 で観測を受信し、学習済み方策の操舵値を配信する。Pi が HTTP コマンドに変換し、ROBOBIKE へ送信する。

### 4. 工夫した点と講義からの発展

**【既存機体を学習対象にする橋渡し】** ファームウェアの操作 API・ステータス・IMU データ形式を調査し、ROS2 のトピックへ対応付けた。講義の ROS2 によるデータ収集と LeRobot による模倣学習を、実機固有の通信仕様を持つ二輪ロボットへ展開した点が、本課題の独自の実装である。

**【通信の遅延・途絶への対応】** HTTP 送信を別スレッドで実行し、未送信の操舵値は最新値へ置き換える。停止命令は待ち行列を破棄して優先し、失敗時には再送する。方策入力が 0.5 秒以上古くなった場合は操舵を停止し、再開には START 操作を必要とする。ウォッチドッグを有効にすると、最初の方策ハートビート受信後、0.5 秒の途絶を検知して緊急停止命令を送る。ただし、機体との通信自体が失われた場合の停止を保証するものではない。

**【学習と ROS2 の環境差を吸収】** 学習は Python3.12、ROS2 を利用する変換・推論は Python3.14 で行う。使用環境で生じた設定読み込みライブラリの互換性問題に対し、ACT の設定・重み・前後処理を直接読み込む処理を実装した。また、実機なしで通信処理を確認できるダミーサーバを用意した。

### 5. 実施結果と到達点

保存済みの実機データセットと学習チェックポイントを確認した結果を以下に示す。これらは学習処理の実行実績であり、走行性能を示す数値ではない。

| 確認項目 | 結果 |
|---|---|
| 実機データセット | `real_v0`：14 エピソード、894 フレーム、10Hz（フレーム数換算で約 89.4 秒） |
| ACT学習 | `real_v0_smoke`：3,000 ステップのチェックポイント保存を確認。バッチサイズ 8 |
| システムの接続 | 収集 → 変換 → 学習 → 推論 → 実機へのコマンド送信まで動作確認済み（リポジトリREADME記載） |
| 走行タスク | 学習済み方策による走行は未達。成功率・連続走行時間などの定量評価は未実施 |

データ量と学習条件の根拠は、データセットの `meta/info.json`、チェックポイントの `train_config.json` および `training_state/training_step.json` である。これらの学習成果はコードリポジトリとは別のデータ保存先で管理している。動画は実機での取り組みを示す提出物として冒頭の URL に公開している。

### 6. 課題・考察と今後の改善

最大の課題は、ゲームパッドによる手動走行でも転倒しやすく、模倣するための良質な走行データを十分に収集できなかったことである。今回の約 89 秒分のデータと 3,000 ステップの学習では、システムの接続確認までにとどまった。学習処理が完了することと、実機で目的の行動を安定して再現することは、別に検証する必要があると分かった。

二輪ロボットでは、機体の状態、速度、操舵、通信・観測の遅延が走行に影響する。現状の受信時刻による対応付けは実装しやすい一方、センサでの取得時刻や操作が実機に反映される時刻まで一致させるものではない。また、現在は速度を人が決めるため、操舵方策の評価でも速度条件を揃える必要がある。

今後は、まず開始姿勢・速度・短い走行区間を固定し、安定した手動走行の収集を優先する。転倒や復帰操作を区別して教師データの品質を確認し、評価用の走行を学習用から分離する。その上で、同じ条件で手動操作と方策操作を比較し、転倒までの走行時間、コースからの逸脱、介入回数を記録する。並行して通信遅延と観測の時間差を計測し、入力の対応付けと行動列の実行ステップ数を見直す。操舵の安定性を確認した後に、速度制御の学習へ拡張したい。

本課題を通じて、既存のロボットへ AI を適用するには、モデルだけでなく、操作インターフェース、観測と行動の対応付け、実機で繰り返しデータを集める仕組みが必要であることを学んだ。構築した Bridge は、その改善と評価を継続するための基盤として利用できる。
